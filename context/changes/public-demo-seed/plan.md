# Public demo account on production — Implementation Plan

## Overview

Roadmap S-09 (`public-demo-seed`, FR-014, NFR "prywatność danych źródłowych"): a reviewer opens
`https://rytm-phi.vercel.app`, signs in to one shared demo account and sees the imported synthetic ING statement with
its patterns. The owner creates and fills the account through the app's own UI. The server recognises the account
by `DEMO_EMAIL` and refuses the actions that would lock other reviewers out, empty the demo, or let someone upload a
real statement to a shared account. Credentials are published in the README and the submission text.

## Current State Analysis

- The synthetic statement `test/fixtures/ing/Lista_transakcji_nr_0000123456_010926.csv` has 12 months and 2 accounts.
  The default account imports 206 debits. The file is byte-compatible with a real ING export, so the import wizard
  takes it as is. It is generated by `npm run fixture:ing` and checked by `fixture:check`.
- The import path is `src/pages/api/imports.ts:12-78`. The wizard parses the CSV in the browser and posts a JSON
  `payload`. The endpoint then calls the RPC `import_ing_statement` (security invoker, RLS). An overlapping period
  goes to `/imports/new?error=overlap`.
- Account-level actions are in `src/pages/api/auth/password.ts` (password change) and `src/pages/api/auth/delete.ts`
  (RPC `delete_own_account`, which cascades everything). Undoing an import is `src/pages/api/imports/delete.ts`.
- All four endpoints share one shape: `createClient` → `getUser()` → zod → redirect with a `?error=<code>`.
- Pages map those codes to copy:
  - `src/pages/settings.astro:18-24,75`
  - `src/pages/imports/index.astro:43-51`
  - `src/pages/imports/new.astro:28` (`z.enum(["overlap","invalid","failed"])`, passed to `ImportWizard.tsx:35`)
- No sanctioned path writes rows to production:
  - `supabase/seed.sql` is local/CI only.
  - Migrations ship only from the CI `deploy` job (`ci-db-push`).
  - Local `permissions.deny` blocks hosted Supabase commands.
  - Smoke must never run against production (CLAUDE.md).
- Production requires e-mail confirmation (`deploy-plan.md:145`), so the demo account needs a real inbox.
- Nothing protects a shared account. Any signed-in user can change the password (S-08), delete the account, undo
  the import (S-02), import files, set thresholds (S-04) and make pattern decisions (S-05).
- The schema has no role and no `is_demo` concept.
- Env vars are declared in `astro.config.mjs` `env.schema` and read through `astro:env/server`. On Vercel only a
  human adds them (deploy-plan operating model).
- Copy the design kit lacks goes to `copyExtra` in `src/content/copy.ts` with a `DESIGN-GAP` comment, plus a row in
  `context/foundation/design-kit.md`. The last gap row is G36.

## Desired End State

- The owner has signed up `DEMO_EMAIL` on production, confirmed it, and imported the fixture's default account
  through the wizard. `/patterns`, `/fixed` and `/home` show the synthetic data.
- For the account whose e-mail equals `DEMO_EMAIL` (trimmed, case-insensitive), the server refuses:
  - a password change → `/settings?error=demo-password`
  - an account deletion → `/settings?error=demo-delete`
  - undoing an import → `/imports?error=demo`
  - a new import when the account already has at least one import → `/imports/new?error=demo`
- Each refusal shows one Polish sentence where the existing error for that form appears. Thresholds and pattern
  decisions keep working.
- Any other account behaves exactly as today. With `DEMO_EMAIL` unset, no account is treated as demo.
- The README has a "Demo" section with the URL, e-mail and password. `deploy-plan.md` records how to seed and reset
  the account.

### Key Discoveries:

- The guard must run before the RPC in `imports.ts`. A second import of the same period would otherwise surface as
  `overlap` instead of `demo`. This order is also what the smoke step asserts.
- An RLS-scoped `imports` count gives the "first import" check without a migration.
- A reset needs no code. The owner deletes the demo user in the Supabase dashboard (the cascade removes every row,
  CLAUDE.md hard rule), signs up again and re-imports. That first import is allowed because the account is empty.
- Local smoke needs a confirmed demo user. It goes into `seed.sql` with a fixed UUID, following the existing
  test-user block (`seed.sql:10-43`).

## What We're NOT Doing

- No migration, no role column, no DB-level guard. The guard is app-level, keyed on `DEMO_EMAIL`.
- No read-only demo. Thresholds, pattern decisions (merge, exclude, type, name) and fixed-cost pinning stay usable,
  so visitors can drift the demo state and the owner resets it by hand.
- No demo credentials or demo button on `/login` (no new UI outside the kit).
- No hiding or disabling of the blocked forms. They submit and show the refusal message.
- No script, migration or agent that writes demo data to production. Seeding and reset are owner steps in the UI and
  the Supabase dashboard.
- No scheduled or automatic reset of the demo state.
- No second demo account and no import of the fixture's second account ("Rachunek VAT").

## Implementation Approach

1. Add one pure rule module plus a thin env read.
2. Put a guard at the top of four endpoints, right after `getUser()`.
3. Add new `?error=` codes and copy on the three pages.
4. Seed a local confirmed demo user and extend the smoke test so CI proves the guards against a real server.
5. Document the owner procedure.
6. Roll out: the env var goes on Vercel before the merge, and seeding happens after the deploy.

## Critical Implementation Details

**State sequencing** — On production, `DEMO_EMAIL` must be set on Vercel before the merge deploy, and the owner
imports only after that deploy. If the account is seeded while the guard is off, a visitor could undo the import
before the guard lands. The first import is allowed only while the account has zero imports, so seeding after the
deploy works.

## Phase 1: Demo-account guard in code

### Overview

Recognise the demo account on the server and refuse four actions for it, with messages in the existing error slots.
Prove it with unit tests and smoke steps that run in CI.

### Changes Required:

#### 1. Env var

**File**: `astro.config.mjs`, `.env.example`, `.github/workflows/ci.yml`

**Intent**: Make the demo e-mail a runtime server setting that is absent by default on production until the owner
sets it. Locally and in CI it is fixed to the seeded demo user.

**Contract**:
- `env.schema.DEMO_EMAIL`: `envField.string({ context: "server", access: "secret", optional: true })`.
- `.env.example` gains `DEMO_EMAIL=demo@rytm.local` with a one-line comment: the demo account's guard, and on
  production the owner sets it on Vercel.
- The smoke job's "Configure secrets for the dev server" step writes a `DEMO_EMAIL=demo@rytm.local` line into `.env`
  next to `SUPABASE_URL` / `SUPABASE_KEY`.

#### 2. Rule module

**File**: `src/lib/demo.ts` (new)

**Intent**: Keep the decisions pure and unit-testable, next to `src/lib/auth-rules.ts` in style.

**Contract**:
- `isDemoEmail(email: string | undefined | null, demoEmail: string | undefined): boolean`
  - `false` when either value is empty.
  - Otherwise compares `trim().toLowerCase()` of both.
- `demoImportAllowed(existingImports: number): boolean` returns `existingImports === 0`.
- `DEMO_ERROR` redirect targets:
  - `password: "/settings?error=demo-password"`
  - `delete: "/settings?error=demo-delete"`
  - `undo: "/imports?error=demo"`
  - `import: "/imports/new?error=demo"`
- The endpoints read `DEMO_EMAIL` from `astro:env/server` and pass it in. The module itself does not import
  `astro:env`, so Vitest loads it without Astro.

#### 3. Guards

**Files**: `src/pages/api/auth/password.ts`, `src/pages/api/auth/delete.ts`, `src/pages/api/imports/delete.ts`,
`src/pages/api/imports.ts`

**Intent**: Refuse the four actions for the demo account before any validation or RPC, so the outcome does not
depend on form contents.

**Contract**:
- Right after the `if (!user)` redirect: `if (isDemoEmail(user.email, DEMO_EMAIL)) return context.redirect(DEMO_ERROR.<x>)`.
- In `imports.ts` only, the redirect is conditional. The endpoint counts the caller's imports with
  `supabase.from("imports").select("id", { count: "exact", head: true })` (RLS scopes it). It redirects when
  `!demoImportAllowed(count ?? 1)`. A count error counts as "not allowed" (fail closed).
- The existing comment style applies: one line that names S-09 and the reason (shared public account).

#### 4. Messages

**Files**: `src/content/copy.ts`, `src/pages/settings.astro`, `src/pages/imports/index.astro`,
`src/pages/imports/new.astro`, `src/components/imports/ImportWizard.tsx`, `context/foundation/design-kit.md`

**Intent**: Show one sentence where each blocked form already shows its errors. The kit has no such state, so it is a
recorded design gap.

**Contract**:
- `copyExtra.settings.demoLocked`: „To jest wspólne konto demo — zmiana hasła i usunięcie konta są wyłączone.”
  - Rendered by `settings.astro` as `passwordError` for `demo-password` and as the delete form's `serverError` for
    `demo-delete`.
- `copyExtra.imports.demoLocked`: „To jest wspólne konto demo — dodawanie i cofanie importów jest wyłączone.”
  - Rendered as the `/imports` status (`kind: "error"`) for `?error=demo`.
  - Rendered by the wizard for `kind: "demo"`: `new.astro`'s enum gains `"demo"`, `WizardServerError.kind` gains
    `"demo"`, and the wizard error branch renders this text.
- Both keys carry `// DESIGN-GAP: G37 — …`.
- `design-kit.md` gains row G37: "Stan konta demo (S-09, FR-014): kit nie definiuje odmowy akcji na wspólnym
  koncie", mapping the two strings to the four codes.

#### 5. Local demo user and smoke

**Files**: `supabase/seed.sql`, `scripts/smoke.mjs`

**Intent**: Give local runs and CI a confirmed demo user, and prove each guard against the running server.

**Contract**:
- `seed.sql` adds `demo@rytm.local` / `Rytm-Demo-Passw0rd!`, UUID `22222222-2222-4222-8222-222222222222`. It copies
  the test-user block (users + identities, `on conflict do nothing`) and gets a header comment line.
- `smoke.mjs` adds a `demo` credential constant and these steps before the final seeded-user section, in order:
  1. demo signs in → `/home`
  2. demo imports the existing small payload
     - Expected location prefix is `/imports/`: the first run creates the import, and later local runs are refused.
     - This step only guarantees that the account has an import.
  3. demo imports the same payload again → `/imports/new?error=demo`, not `overlap`, which proves the guard order
  4. demo `POST /api/imports/delete` with a random UUID → `/imports?error=demo`
  5. demo password change with its real current password → `/settings?error=demo-password`
  6. demo delete with its real password and `USUŃ` → `/settings?error=demo-delete`
  7. demo still signs in afterwards → `/home`, which proves nothing was changed
  8. demo signs out
- The seeded test user's existing steps still pass, which proves non-demo accounts are unaffected.

#### 6. Unit tests

**File**: `test/unit/demo.test.ts` (new)

**Intent**: Pin the pure rules.

**Contract**:
- `isDemoEmail`:
  - equal, case-different and whitespace-padded addresses → `true`
  - a different address → `false`
  - either side undefined or empty → `false`
- `demoImportAllowed(0)` is `true`; `demoImportAllowed(1)` and `demoImportAllowed(3)` are `false`.

### Success Criteria:

#### Automated Verification:

- Unit tests pass, including `test/unit/demo.test.ts`: `npm test`
- Lint passes: `npm run lint`
- Type and Astro check pass: `npx astro check`
- Build passes: `npm run build`
- Local DB reset applies the new seed and pgTAP still passes: `npx supabase db reset && npx supabase test db`
- Smoke passes against `npm run dev` with `DEMO_EMAIL=demo@rytm.local` in `.env`, including the 8 new demo steps: `npm run smoke`

#### Manual Verification:

- Locally, signed in as `demo@rytm.local`, each of the four refusals shows its sentence in the right place (`/settings` password form, `/settings` delete form, `/imports`, the wizard)
- Locally, the demo account can still set a threshold and merge or exclude a pattern

## Phase 3: Rollout and seeding on production

### Overview

Owner steps plus agent-side verification. The guard lands first, then the account is seeded, then the credentials are
published.

### Changes Required:

#### 1. Owner steps (human)

**Intent**: Create and fill the demo account without any agent or script touching production data.

**Contract**:
1. Choose the demo address (a real inbox, e.g. a Gmail `+` alias) and a strong password that will be published.
2. `vercel env add DEMO_EMAIL production` with that address.
3. Merge the PR, then wait for the green `deploy`.
4. On `https://rytm-phi.vercel.app`: sign up, confirm the e-mail, sign in, and in the wizard import
   `test/fixtures/ing/Lista_transakcji_nr_0000123456_010926.csv`, default account.
5. Check the four refusals on production.

#### 2. Publish credentials

**Files**: `README.md`, `context/deployment/deploy-plan.md`

**Intent**: Replace the README placeholders with the real e-mail and password, and record the seeding date and the
import result (206 debits) in the demo section.

**Contract**: `README.md` § Demo filled in. `deploy-plan.md` § Demo account gains a dated "Seeded" line.

### Success Criteria:

#### Automated Verification:

- The merge run is green for `ci`, `smoke` and `deploy`: `gh run view <run> --json jobs`
- `https://rytm-phi.vercel.app/login` answers 200: `curl -s -o /dev/null -w '%{http_code}' https://rytm-phi.vercel.app/login`

#### Manual Verification:

- `DEMO_EMAIL` is set on Vercel production before the merge (`vercel env ls` lists it)
- Signed in as the demo account on production, `/imports` shows one import of 206 debits and `/patterns` lists the synthetic patterns
- On production, the demo account's password change, account deletion, import undo and second import are refused with the demo sentence
- The README Demo section has the real credentials, and signing in with them works from a private window

**Implementation Note**: The PR must not merge before step 2 (the env var). Seeding happens only after the merge
deploy is green.

## Testing Strategy

### Unit Tests:

- `isDemoEmail` normalisation and empty handling.
- `demoImportAllowed` boundary at 0 and 1.

### Integration Tests:

- Smoke (local and CI):
  - the demo account is refused on all four endpoints;
  - the second import is refused as `demo` before the overlap check;
  - the demo account can still sign in after the refused password change and deletion;
  - the seeded non-demo user is unaffected.

### Manual Testing Steps:

1. Locally as `demo@rytm.local`: trigger each refusal in the UI and read the message placement.
2. Locally as `demo@rytm.local`: set a threshold and exclude a pattern, and confirm both work.
3. On production after seeding: repeat 1 and 2, and sign in from a private window with the README credentials.

## Migration Notes

No schema change. `seed.sql` gains a local-only user and is never applied to production. Rolling back the guard
means unsetting `DEMO_EMAIL` on Vercel and redeploying. The demo account then behaves like any other account.
